# N4.1-B early/late visual acceptance

## Decision entering this slice

The matched offline N4.1 campaign nominated `n41-b`, but the R3 live review
rejected its clockwork walking: 32 complete bouts used one speed and their
duration and distance had R-squared above 0.9999. R4 therefore adds the
separately identified `n41-b-natural` product-prior profile. The frozen N4 and
N4.1-A/B/C artifacts remain byte-identical. This authorizes another live visual
review only, not promotion, deployment, shortcut changes, or replacement of
the frozen artifacts.

## R4 evidence-collector recovery

The exact R4 Windows implementation passed every source, Rust, Clippy, native,
determinism, boundary, build, and preservation check. It committed and
non-force pushed the R4 source, then completed the full ten-minute live run.
The collector failed only when the first complete autonomous Walk bout was
added to a newly created generic list. Windows PowerShell rejects an empty
collection supplied to a mandatory collection parameter unless the parameter
explicitly permits that state. The same latent defect affected the deliberately
supported zero-bout numeric paths.

The preserved R4 trace is complete. An independent replay of its declared gate
produced 81 autonomous complete Walk bouts, duration CV `0.932981`, 39 bouts at
or below one second, seven bouts at or above 4.5 seconds, speed CV `0.364328`,
duration-distance R-squared `0.806080`, `6791.600` pixels of walking, zero
stationary-rotation pairs, four grooming bouts, and all six grooming substates.
Every objective natural-motion condition passes. This replay recovers objective
evidence only: the R4 crash occurred before late ratings and the explicit owner
decision were written, so it does not constitute visual acceptance.

The review-repair slice makes no Rust, parameter, motor, or behavior change. It
explicitly permits empty collections on all five metrics parameters that
support them, adds a hash-recorded offline trace measurement command, and adds
synthetic zero-bout and first-bout regressions. A fresh owner review remains
required before the convergence checkpoint can be accepted.

## Double opt-in boundary

The ordinary application build has an empty default feature set and continues
to call the frozen N4 constructor. N4.1-B-natural can enter the desktop application only
when both controls are present:

1. compile with Cargo feature `n41-visual-review-b`;
2. launch that binary with `--n41-b-visual-review` and an absolute
   `--n41-visual-review-receipt` path.

The candidate writes a launch receipt before creating a window. It records the
active profile, immutable parameter identity, executable SHA-256, source
identity, isolated storage path, and explicit denial of promotion/deployment.
The review pet is visibly titled `MechoFly N4.1-B visual review pet`.

## No-AppData rule

The launcher sets `MECHOFLY_DATA_DIR` to its Downloads-only run directory.
Runtime-profile reads, diagnostic logs, learning state, import manifests, and
exports honor that override. The real `%LOCALAPPDATA%\MechoFly` tree is hashed
before and after the run and must remain identical. The collector never uses a
temporary or AppData directory.

## Ten-minute live protocol

The single-owner formative review uses the exact feature-gated candidate EXE:

| Boundary | Purpose | Evidence |
|---|---|---|
| 0–30 seconds | Early-session behavior | Live observation, early rating, capture at 30 s |
| 30 seconds–5 minutes | Natural warm-up | Candidate remains live; no accelerated model time |
| 5–10 minutes | Late-session behavior | Live observation and captures at 5, 7.5, and 10 min |
| 10 minutes | Explicit decision | Late rating and exact-binary guarded-next-step confirmation |

At both early and late review, the owner rates:

- responsiveness to hover/click/bounded interaction;
- natural, alive, stateful behavior rather than stuck or mechanical behavior;
- acceptability as a non-disruptive desktop companion.

All six criteria plus the final exact-binary confirmation must pass for
`ACCEPTED_FOR_GUARDED_NEXT_STEP`. A rejection is a valid experimental result.
It stops promotion and points back to parameter/product iteration; it is not an
implementation failure.

## Capture privacy

No screen rectangle is captured. The review build renders a 420 × 280 image
directly from the pet's premultiplied BGRA buffer and composites it over a
constant RGB `(28, 24, 36)` backdrop. Uploaded images therefore cannot contain
desktop or application pixels behind the transparent pet. Every boundary
capture records its SHA-256, dimensions, elapsed time, visible-pixel count, and
`full_desktop_captured: false`.

The build also emits a JSON-lines position/heading trace and the first visible
head-sweep, foreleg-rub, abdomen-brush, and wing-clean frame. Acceptance now
fails when walking rotates in place, lacks a broad short-tailed/long-tailed bout
distribution, keeps one walking speed, retains a near-perfect duration-distance
relationship, or provides no structured grooming evidence. The collector
closes only its own candidate before reading the trace so the writer cannot
leave a locked or truncated file. The exact engineering gates and scientific
claim boundary are in `docs/N4.1-Natural-Motion-Correction.md`.

`tools/Measure-N41NaturalMotionEvidence.ps1` can replay this objective gate
without launching a pet. It loads the metrics functions from the exact
collector being measured, hashes the collector, trace, and captures, and writes
an offline receipt. `tools/Test-N41VisualReviewMetrics.ps1` proves that both an
empty Walk distribution and the first completed Walk bout in an initially empty
list are accepted by parameter binding and measured without an exception.

## Exact-binary and process rules

- The candidate executable remains inside the evidence package with its hash.
- The collector refuses to run while any existing `MechoFly.exe` is active.
- It launches one candidate and stops only that process.
- It does not call the installed start/stop scripts.
- It does not modify or read shortcuts.
- It does not copy a binary into `host-windows/bin` or any deployed location.
- It does not modify DesktopFly.

## Required outcome

The evidence ZIP contains the committed source diff/archive, canonical and
candidate build hashes, self-test and integration receipts, the candidate EXE,
privacy-safe captures, human ratings, AppData/shortcut/DesktopFly preservation
receipts, logs, and a manifest. Regardless of visual acceptance, the manifest
continues to state:

```text
promotion_authorized = false
deployment_authorized = false
```

If the exact candidate is accepted, the next separately authorized step is an
internal/dogfood candidate package and guarded promotion design. It is not an
automatic deployment.

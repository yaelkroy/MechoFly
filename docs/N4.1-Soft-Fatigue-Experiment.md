## Why this slice exists

The 200-run N4 campaign passed its declared controller invariants and repeat
identity, but its late-session product behavior was too suppressive:

```text
sustained-walk first 30.03 s     82.98% Walk
sustained-walk final 5 min       36.49% Walk
mixed final 5 min                 0.00% Walk
```

N4 adds 20 fatigue units per walking frame, recovers 12 per Quiet/Rest frame,
and blocks every ordinary external candidate at fatigue 26,000. Those are
authored engineering priors, not fitted physiology. Passing the N4 engineering
campaign therefore does not justify deploying that product policy.

## Experimental policy

N4.1 keeps bounded Q15 state, deterministic duration draws, emergency looming
priority, minimum dwell, cooldowns, and exact checkpoint replay. It replaces the
binary ordinary-input block with a graded response gate:

```text
fatigue <= onset:       response gain = 32767
onset < fatigue < full: response gain decreases linearly in integer Q15
fatigue >= full:        response gain = configured nonzero floor
```

At an ordinary candidate review, a stable event-keyed Q15 draw is derived from:

```text
model seed
controller transition sequence
candidate behavior
context bucket
parameter salt
separate fatigue-response domain tag
```

The candidate is eligible when `draw <= gain`. The draw is stable during the
same bout/context bucket, so this is not a frame-rate lottery. Recovery can
increase gain; a new controller transition creates a new deterministic review
key. Looming bypasses this mechanism completely.

This is a product-engineering experiment. The gain, rates, and response floor
are not probabilities measured from flies, metabolic energy, sleep pressure, or
biological fatigue constants.

## Matched experiment

`n41_experiment` runs `n3`, frozen-default `n4`, and all three N4.1 candidates in
separate processes. Every profile receives the same five scenarios, graph
seeds, model seeds, stimulus function, modeled duration, and repeat count.

The default AI100 matrix is:

```text
5 profiles
5 scenarios
2 graph/model seeds
2 exact repeats
600 modeled seconds per run
100 total runs
```

Each model step records bounded histograms for:

```text
neural compute
intent construction
controller selection
state transition / telemetry
summary state hashing
total step
```

The Python supervisor starts one profile per process, streams progress, samples
working set, hashes every report, and seals a matrix envelope. Timing and memory
are excluded from deterministic signatures. Behavioral results, neural state,
controller state, occupancies, invariants, and unresponsive intervals are
included.

## Gates

A candidate can proceed only to visual review when all of these hold:

```text
all exact-repeat groups equal
zero controller/invariant violations
50% <= sustained-walk final-five-minute occupancy <= 70%
mixed final-five-minute Walk > 0%
quiet-session Quiet + Rest > 50%
incremental behavior-pipeline CPU <= 5% of matched N3 total step
separately sampled working-set increase <= 10 MiB
```

The CPU measure is the candidate's incremental intent + controller + telemetry +
summary-hash time relative to the same components in matched N3, divided by N3
total step time. Neural time is reported separately so scheduler or neural-work
variance is not misreported as controller overhead.

The evaluator reports the Pareto frontier and may nominate one profile for
early/late visual review. It always writes `promotion_authorized: false`. No
offline winner becomes the pet until a later visual-acceptance step validates
responsiveness, naturalness, non-disruption, and the exact tested binary.

## Required validation order

1. Format, locked tests, and warnings-denied Clippy.
2. Build the full Windows app and run its native self-test.
3. Run the default N4 2×2×30-second smoke and compare all 10 frozen signatures.
4. Build the release `n41_experiment` binary.
5. Run the five-profile process-isolated matrix.
6. Evaluate behavioral, performance, and memory gates.
7. Commit and push only the experiment branch.
8. Produce one `UPLOAD_MechoFly_N4_1_Foundation_*.zip` containing source diff,
   identities, logs, reports, evaluation, and manifest.

Failure at any step stops the sequence, authorizes no deployment, and still
produces a diagnostic upload ZIP.
